# Versioning and releases

Use Conventional Commits and Semantic Versioning. `fix` changes patch, `feat` changes minor, and incompatible public contract changes major. During 0.x development, document breaking changes prominently and increment the minor version. Keep workspace package versions aligned until independent releases are justified; source workspace packages remain private; the separately built `dist/npm` artifact is the intended public `open-skill-kit` package. See the [npm distribution guide](npm-distribution.md).

Add user-visible changes to `CHANGELOG.md` under Unreleased in each PR. Skill metadata versions are independent: increment them whenever the skill package changes. Maintainers review provenance and safety again for substantive changes.

For a release, run all README checks from a clean checkout with the frozen lockfile, review the dependency audit, verify status and claims, move Unreleased entries to a dated version section, update package versions and lockfile, and review the diff. Tag `vX.Y.Z` and publish release notes only with explicit maintainer authorization. Deployment and release automation remain outside this batch. No release has been published. Git origin now points to the user-specified GitHub repository; npm publication remains a separate authorized action.

First-release preparation is tracked in the [owner checklist](launch/CHECKLIST.md), [per-skill summaries](launch/SHORTLIST_REVIEW.md), [repository settings guide](launch/GITHUB_SETTINGS.md) and [preparation report](launch/PREPARATION_REPORT.md). Current content remains draft and unapproved; the shortlist is a review proposal only. Never infer commit, push, visibility, hosting or publication permission from a successful local suite.

## Fail-closed dependency release preflight

Ordinary local builds collect notices for diagnostics and do not grant release permission. Explicit release preparation must use `pnpm exec tsx scripts/build-npm.ts --release` for npm, and `OPEN_SKILL_KIT_RELEASE_BUILD=1 pnpm build` for the browser. The npm default is a private diagnostic package whose publication guard rejects it. Release npm preparation checks licensing before writing output and still requires approved published skills. Browser release preparation checks licensing before Rollup writes the bundle. No automated deployment or publication workflow exists. Manually uploading a diagnostic build would bypass the prescribed release procedure and is not authorized.

The shared gate checks only actually distributed dependencies against unchanged canonical evidence and actual packaged notices. It rejects any unresolved notice record, changed/missing evidence and override-only notices. Exact-release packaged evidence must be nonempty UTF-8 with matching canonical manifest/notice bytes; hashes and version declarations alone are insufficient. Cross-version override limitations remain visible in local notices but cannot clear this gate. No licensing-approval schema or exception waiver is introduced, and passing this negative technical preflight never replaces rights review or explicit owner authorization. Unbundled development/native tooling still requires evidence before redistribution.

The current react-remove-scroll-bar@2.3.8 browser dependency remains blocked: its retained notice is sourced from 2.3.7 and canonical status is human-confirmation-required. Neither removing the limitation nor copying an old notice into the installed package supplies legitimate clearance. Genuine exact-release provenance or a separately approved replacement is still required.
