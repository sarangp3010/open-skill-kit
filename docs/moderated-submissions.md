# Moderated skill submissions

The browser editor at /create is free and account-free. It can create/edit text packages, show sanitized Markdown previews, run the existing schema/reference/package validator and structural-quality rubric, save unfinished drafts as JSON, import those drafts, and export complete proposal ZIPs. It never uploads a package, writes the catalog, calls a model or authenticates to GitHub. Drafts stay in the tab's memory until exported; refreshing can discard unsaved work. Do not put private data or secrets in a proposal.

**Submit Skill means prepare a GitHub pull request for review. It is not publication.** A valid package enables the PR guide and ZIP export, but no browser operation grants approval. GitHub login and repository access are needed only on GitHub. Existing 42 source drafts remain accessible through the explicitly labeled draft/source library and their unchanged URLs. The separate /published view consumes published.json; it starts empty because no actual publication approval has occurred. A source metadata status is not evidence of publication.

## Create and submit

1. Open Create from the contribution page. Choose a canonical collection, enter a unique skill name and apply its identity. Replace the template's illustrative workflow, author/provenance and examples with your actual task. Required identity fields are synchronized; content remains editable.
2. Edit SKILL.md, metadata.json, examples and tests/cases.json using the file selector. Add/remove admitted supporting files as needed. The existing limits apply: up to 100 files, 256 KiB/file and 1 MiB total UTF-8 content, safe portable relative paths and admitted Markdown/JSON/TXT/CSV only. Reserved submission.json is generated by the editor. Unsafe paths, scripts and binary/NUL content are refused. Markdown previews never execute embedded HTML or scripts.
3. Validate. The report lists actual file errors and advisory rubric checks. Quality is structural, not model effectiveness. Browser proposals must remain draft with no legacy tested-platform/date claims. Contributor identity and compatibility are not automatically verified. Existing identifiers are checked against the source library; CI repeats those checks authoritatively.
4. Export a ZIP when valid. It retains the complete admitted package and a submission.json request. Extract the slug folder into submissions/{canonical-sector}/ in your fork, producing submissions/{sector}/{slug}/SKILL.md. Do not copy it directly into skills/ or alter the publication review ledger. Save JSON separately for unfinished work; JSON imports are bounded and rechecked rather than executed.
5. Run pnpm contributions:check, pnpm moderation:check, pnpm skills:index and pnpm validate:all. Add relevant offline suites under evaluations/scenarios if useful. They use the existing Phase 4 runner; suites targeting a staged update read that staged package, not the older source version. Authored fixtures remain explicitly fixtures, never actual agent results.
6. Use the Submit Skill guide's GitHub compare link to open your own **draft PR**. Include the whole proposed folder, task/activation/limitations, provenance/licenses, example coverage and exact validation results. The editor does not create the PR or publish on your behalf.

Unapproved submissions live only under submissions/. That directory is inspected by CI but is never indexed, copied into website assets, included in sitemaps, or bundled by npm. No placeholder skills appear merely because a proposal exists. Updating submissions/ cannot overwrite the active skills/ package.

## Automated review

The existing contribution checker now inspects both source and pending packages. It validates canonical schema, package safety, local references, duplicate slugs/identifiers and normalized instruction-body copies, and reports quality with individual results. New proposals cannot collide with existing IDs; an intentional update requires the matching base package digest. A submitted published status is rejected. Supplied evaluation suites run offline in isolated temporary workspaces through Phase 4. All existing tests, link/catalog checks, builds, accessibility and packaging still run. None of these deterministic checks verifies an identity, professional decision or skill effectiveness.

The publication gate has two layers:

- Local builds check the separate catalog/publication-reviews.json ledger, authorized reviewer registry, exact package digest and authored publication status. No ledger record or a stale/withdrawn record means exclusion from published.json and npm bundles. Changing metadata to published alone never admits a skill.
- In GitHub Actions, the read-only moderation step checks actual GitHub PR/review data. A new or changed decision must reference the current PR, not an unrelated historical approval. The reviewer must be authorized by the **trusted base** maintainer roster, distinct from the PR author, and have an undismissed approval for the current PR head. Changed source additions need that PR's approval decision. After merge, main checks require the referenced PR to be merged by an authorized maintainer into the canonical repository's main branch and retain the head approval. Missing evidence, stale approvals, rejected/dismissed reviews or an API failure fail closed. No review, comment, merge or publication is performed by this check.

pull_request_review submitted/dismissed events rerun validation, so approval can unblock a prepared promotion and dismissal can invalidate it. Only a read-scoped GitHub token is used for these GET requests; there are no provider secrets, PR write permissions, privileged PR builds or automatic merges. Trusted-main build/deployment permissions remain separate. See [official PR review API](https://docs.github.com/en/rest/pulls/reviews) and [review events](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows).

## Maintainer acceptance and publication

An authorized maintainer reviews scope, usefulness, originality/licensing, privacy, unsafe instructions, examples and limitations. High-stakes content needs suitable domain review. Quality or fixture scores are not approval. The authorized roster initially names only the existing owner; roster changes themselves require owner review. No actual approval records are prefilled.

For an accepted proposal, the maintainer prepares the promotion **within the reviewed PR**:

1. Move the complete accepted package into skills/{sector}/{slug}/ and remove the staging submission.json. Keep pending/rejected material out of the active source. Check every supporting file and preserve existing IDs for updates.
2. Set the approved package's status to published only as part of the promotion; do not add unsupported identity/platform/model claims. Compute the exact final package digest with pnpm moderation:check --digest {sector}/{slug}. Any content/status change changes that digest. This publication digest binds every admitted file, including platform-result records; it is intentionally separate from the existing compatibility digest that excludes its self-referential results file.
3. Complete the [Founding Skills Review procedure](founding-skills-review.md) for the final contents. Manually record the actual reviewer identity, date, substantive checklist answers and hashed evidence; no automated check writes approval. Bind the completed form through reviewRecord (repository-relative path and raw-file SHA-256). Add/update a publication-reviews.json decision containing skillId, packageDigest, decision approved, authorized reviewer, actual review decision time, this PR number and a substantive review reason. Attribution review remains a separate process; publication does not verify identity or compatibility.
4. Regenerate both catalogs with pnpm skills:index, run the full suite, and request an explicit GitHub approval for the final PR head. Committing more changes after approval requires a fresh approval. A maintainer's own PR requires another authorized reviewer; there is no self-approval shortcut.
5. An authorized maintainer merges after review and checks pass. The trusted-main gate rechecks real merged-review evidence before a future Pages build can deploy the approved artifact. Merely exporting, opening a PR, editing a status or passing ordinary package checks does not publish anything.

Only the generated published catalog contains approved/current packages. The historical source/draft library is clearly separate, retains existing URLs, and does not claim those drafts are approved. npm distribution also requires the matching approval decision; it remains a separate manually authorized release, never a browser or PR action.

## Request changes, rejection and updates

A reviewer may request changes with specific evidence gaps. Keep the proposal pending, revise its source/examples, rerun checks and request another review. The latest changes-requested or dismissed review does not count as approval. Rejection means closing the PR without promotion; no published entry is created. A proposal merged for discussion under submissions/ remains unapproved and undistributed. An author may withdraw their own proposal without affecting an existing publication.

For an update, use Propose an update from the source detail page, then explicitly load the original. The editor preserves supporting text files, resets legacy testing/status declarations and records the original package digest in submission.json. Edit locally and submit under submissions/{same-id}/. CI rejects an update whose base no longer matches the active package. Refresh/rebase the proposal and review the differences rather than overwriting a newer version. Acceptance replaces the active package and requires a new exact-package decision/current-head approval; the old receipt cannot approve changed content.

## Withdrawal and removal

For a published withdrawal, open a maintainer-reviewed PR changing the decision to withdrawn with this PR number, actual reviewer/time and reason. Retain the decision rather than erasing review history; Git history preserves prior decisions. The published catalog and future npm bundles exclude withdrawn records even if old metadata says published. A source preview may be retained for transparency with clear source-status labeling; remove the source package only when approved and document resulting URL/removal behavior. Already downloaded packages and published npm releases cannot be remotely revoked by this static site. Explain affected IDs/versions and remediation in the PR/release notes. Sensitive-data or security removals use the private reporting policy and a separately approved response; do not paste harmful material into public notices.

## Deployment and trust limitations

The repository implementation cannot grant or enforce GitHub account permissions by itself. The owner must require the CI validation/moderation check and maintainer reviews in whatever branch/environment controls are available under the repository's existing free plan, restrict merge/write rights and protect workflow/roster/ledger changes. CODEOWNERS alone is not enforcement. No remote protection setting, visibility or paid feature was changed in this task. A trusted administrator can alter repository policy; no local script can prevent that. Missing required-review enforcement is an explicit public-readiness configuration item, not a claim that it is already enabled.

All implementation changes and local validation remain uncommitted. No PR, merge, push, publication, deployment, real contributor approval or real agent test is performed by implementing this workflow.
